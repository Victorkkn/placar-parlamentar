# 0010 — Isolating the summary feature and enforcing source links

- **Status:** accepted (2026-11-01)
- **Date:** 2026-11-01
- **Stage:** 2 (topic 7 of 10)

## Context

The app shows a short, neutral summary of each official's public activity in a window. Every factual sentence must trace to an official source link, and a test must enforce it (Phase D). The summary is a feature of the app; the project builds no model evaluation, training or benchmarking pipeline.

Earlier decisions:

- `summaries` may read `core`, `legislators`, `activity` and `metrics`, and every value it returns carries `SourceRef`s (0007).
- Django has no built-in production worker for background jobs (0005).
- Visitors are not tracked and no visitor data is stored (rule 5).

Risks to manage:

- A language model can state things the records do not show, or use judgmental wording.
- Free text in official records (bill descriptions, speech text) could contain instructions that try to steer the model (prompt injection).
- Model calls cost money and can fail or refuse.

Facts checked on 2026-11-01 (Claude API reference): the Messages API supports **structured outputs** (`output_config.format` with a JSON schema; the SDK's `messages.parse()` validates the response). Current models include Claude Opus 5.5 (`claude-opus-5-5`, $4 / $20 per million input / output tokens), Claude Sonnet 5.5 (`claude-sonnet-5-5`, $2 / $10) and Claude Haiku 5.5 (`claude-haiku-5-5`, $0.10 / $0.50). A response can end with `stop_reason: "refusal"`.

## Decision

### Isolation

1. All summary code lives in `backend/placar/summaries/`. The language model is reached through **one adapter module** (`summaries/llm/`). It is the only code allowed to import the model provider's SDK; the boundary test (0007) enforces this.
2. **Provider:** the Claude API through the official `anthropic` Python SDK.
   - The model is set by an environment variable (`SUMMARY_MODEL`). The default is `claude-opus-5-5`; the project owner may choose a cheaper model.
   - The API key comes only from `ANTHROPIC_API_KEY` in the git-ignored `.env`, under the owner's personal account.
   - Without a key, the app still works and shows template summaries only (item 9).
3. **Only public official data is sent** to the provider. Never visitor data, and never text typed by visitors.

### Input: a fact sheet

4. For an official and a window, `summaries` builds a **fact sheet** from `metrics` and selectors. It is a list of facts, each with an id, a type, structured values (numbers, dates, counts, names of officials and parties) and its `SourceRef`s.
5. **No free text from the APIs in the MVP.** Bill topics use the official theme codes and names, not bill descriptions or speech text. Adding free text later needs a new decision, which must pass it as clearly marked data.

### Output and checks

6. The model must answer in a **fixed JSON format** (structured outputs): a list of sentences in pt-BR, each with the ids of the facts it relies on.
7. A **validator in plain Python** checks every draft. The whole draft is rejected if any check fails:
   - every sentence cites at least one fact id, and every cited id exists in the fact sheet;
   - every number and date in a sentence appears in its cited facts (compared after pt-BR formatting);
   - every official or party name in a sentence appears in its cited facts;
   - no word or phrase from the **banned-wording list** (judgmental terms in pt-BR, kept by the technical writer in `summaries/wording/`);
   - limits on sentence count and length.
8. A rejected draft, a refusal, an error or a timeout leads to **one retry**. If that also fails, the app uses the **template summary**.
9. **Template summary:** fixed pt-BR sentences filled in from the same fact sheet, with the same fact ids. It always passes the validator. It is also the only summary for custom windows.

### When summaries are generated

10. Model summaries are **generated ahead of time** by a management command (for example `generate_summaries`) for the preset windows (current legislature, last two years), never during a visitor's request. No background worker is needed in the MVP.
11. Each stored summary records the model id, prompt version, a hash of the fact sheet, the creation time and the validation result. When the fact sheet changes, the stored summary is out of date and is regenerated by the command.

### Display

12. Each sentence is shown with the source links of its facts.
13. The page says, in pt-BR, that the text was written automatically from official records, and shows whether it is a model summary or a template summary. The methodology page explains both.

### Tests

14. Tests use a **fake adapter**, never the real API. They cover:
   - valid drafts pass;
   - each validator rule rejects a crafted bad draft;
   - fallback to the template summary;
   - every sentence of every stored summary maps to at least one `SourceRef`.

## Alternatives considered

- **Templates only, no language model.** Fully predictable and free, and it always passes the checks; the sentences are more repetitive. Kept as the fallback and for custom windows, but the README asks for an LLM-based summary feature.
- **Generate on each request.** Always fresh, but cost and delay grow with traffic, visitors could trigger paid calls, and it needs a worker or long requests.
- **The Claude API's citations feature** (the model cites spans of provided documents). Useful for documents, but it cannot be combined with structured outputs, and per-sentence fact ids give a simpler, stricter check over structured records.
- **A local model (for example through Ollama).** No data leaves the machine and no per-call cost, but lower quality in pt-BR, needs strong hardware, and the data is public anyway.
- **Another provider.** Possible behind the same adapter; changing provider needs a new decision.

## Consequences

- The backend engineer owns `summaries/`; the technical writer owns the banned-wording list and the template sentences; QA owns the source-mapping test.
- Dependency to approve in Phase D: `anthropic`.
- Cost is bounded: one call (plus at most one retry) per official per preset window, each time the data changes.
- Summaries for custom windows are less varied (templates).
- If the model output drifts, the validator rejects it and the template is shown; no unverified sentence reaches a visitor.
